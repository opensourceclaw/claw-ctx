## TL;DR

本次针对用户反馈的"OpenClaw 会话连续性在 /new 或重启后失效"问题做根因调研，发现 **5 个正常场景缺陷 + 3 个溢出后特有缺陷**。本次完成 **P0 四项修复**，覆盖正常 + 溢出后两种场景下最常见的连续性丢失问题。

P1（Recap 格式不匹配）和 P2（pendingItems 恒空）留待 v5.12.0，工作量较大。

## 1. 问题背景

用户反馈：
1. OpenClaw 执行 `/new` 后会话连续性失效
2. 进程重启后会话连续性失效
3. 会话溢出（context overflow）后执行 `/new` 或重启，连续性失效更严重

## 2. 根因调研

### 2.1 正常场景下的 5 个缺陷

| # | 缺陷 | 位置 |
|---|------|------|
| 1 | `SummaryGenerator` 产 JSON 但 `RecapLoader.parseRecap` 用正则匹配字面量 | `recap-loader.ts:275` |
| 2 | `engine.closeSession` 只清 LRU 缓存，不调 `_checkpointManager.closeSession` | `engine.ts:1138` |
| 3 | `SessionResumeManager.reset()` 在 bootstrap 中从未被调用 | `bootstrap.ts:170` |
| 4 | `CheckpointManager.bootstrap` 的 `getRecoveryContext` 不传 sessionId | `checkpoint.ts:174` |
| 5 | `buildSnapshot.pendingItems` 恒为空数组 | `checkpoint.ts:248` |

### 2.2 溢出后特有的 3 个新缺陷

| # | 缺陷 | 严重度 |
|---|------|--------|
| 6 | `_executeCompaction()` 纯文件操作，不更新 `_sessionState` | **高** |
| 7 | compact 后不调 `_checkpointManager.checkpoint()`，claw-mem 快照是 pre-compaction | **高** |
| 8 | compact 后不调 `manager.store()`，episodic memory 无 post-compaction summary | **高** |

### 2.3 触发链

```
/new 或重启 -> bootstrap(sessionId)
  -> [缺陷3] _sessionResume._history 仍是上一段
  -> [缺陷4] getRecoveryContext 返回所有未关闭（包括刚 closeSession 的）
  -> [缺陷2] 旧 session 未真正关闭，被当作 recovery
  -> [缺陷1] recap 解析失败，注入截断 JSON
  -> [缺陷5] pendingItems 永远空

溢出后路径：
compact 成功
  -> [缺陷6/7/8] 内存态 + 持久化态全部 pre-compaction
  -> 上述 /new 或重启路径全部恶化：注入的 recovery 上下文与磁盘 sessionFile 矛盾
```

### 2.4 OpenClaw 端缺陷（非 claw-ctx 能修）

- `embedded-agent-DGUuxGR2.js:3544-3567` 的 `[context-overflow-precheck]` 调 `contextEngine.compact()` 后只调 `runContextEngineMaintenance()`（仅触发 decayEngine）
- **既不调 `afterTurn()` 也不调 `bootstrap()`**
- `[timeout-compaction]` 路径（L3437-3450）同样只调 `runPostCompactionSideEffects`

**结论**：claw-ctx 必须在 `compact()` 成功路径里自己同步状态，不能依赖 OpenClaw 主动调 afterTurn。

## 3. P0 修复清单

### 3.1 compact 成功后同步状态

**`src/engine.ts:686-745`**

`_executeCompaction()` 返回新增字段：

```typescript
return {
  compacted: true,
  summary: ...,
  tokensBefore, tokensAfter,
  details: {...},
  keptMsgs,        // 新增：保留的消息
  summaryBlock,    // 新增：压缩 summary 块

```

`compact()` 成功路径新增三步同步：

```typescript
if (result.compacted) {
  this._tokenWarningEmitted = false;
  
  // 1. 重建 _sessionState（从 keptMsgs 重新抽取 entities/decisions/topics）
  const extracted = SessionStateExtractor.extract(keptMsgs.map(...), p.sessionId);
  this._sessionState = extracted;
  
  // 2. 持久化 post-compaction 快照到 claw-mem
  await this._checkpointManager.checkpoint(this._sessionState);
  
  // 3. 存 episodic memory 作为 post-compact summary
  this.manager.store(summaryBlock, "episodic", ["compaction", "post-compact"]);

```

**失败非阻塞**：任一同步步骤抛异常只 warn，不影响 compact 主流程。

## 7. 修复效果

### 正常 /new 场景

| 修复前 | 修复后 |
|--------|--------|
| 新 session 继承上一段的 `_history`/`_recap` | reset() 清空，干净启动 |
| 旧 session 被当作"中断未恢复"注入 | closeSession 标记 `isClosed=true`，不再返回 |
| 当前 session 被当作自己的 recovery | getRecoveryContext 过滤掉当前 sessionId |

### 溢出后 /new 或重启场景

| 修复前 | 修复后 |
|--------|--------|
| compact 后内存态仍引用已删除的消息 | 重建 `_sessionState`，只含 keptMsgs |
| claw-mem 快照是 pre-compaction | compact 后主动调 checkpoint |
| episodic memory 无 post-compact summary | 主动存 `["compaction", "post-compact"]` |
| 重启后 bootstrap 读到 pre-compaction 快照 | 与磁盘 sessionFile 一致 |

## 9. 风险与建议

### 9.1 签名变更风险

`closeSession` 从同步变异步。OpenClaw 代码 grep 确认不直接调此方法（`contextEngine.closeSession` 无匹配），但内部有 2 处调用：
- `engine.ts:1565` `dispose()` 中（已 await）
- 新增的 `engine.ts:1149`（已 await）

### 9.2 compact 后状态重建失败风险

`SessionStateExtractor.extract()` 可能因消息格式异常抛错。已用 try-catch 包裹，失败只 warn，`_sessionState` 保持原状（pre-compaction）。最坏情况：重启后 bootstrap 仍读 pre-compaction 快照，但**不影响 compact 主流程成功**。

### 9.3 建议观察指标

重启 gateway 后观察 1-2 天：
- `[claw-ctx] post-compact state rebuilt: entities=N` 日志频率
- `[claw-ctx] post-compact checkpoint failed` / `post-compact state sync failed` 警告频率
- `/new` 后新 session 的 `[Session Recovery]` 上下文是否合理（不应包含当前 session 自身）
- 溢出后重启，sessionFile 与 recovery context 是否一致

## 10. 后续建议（v5.12.0）

1. **P1**: 重写 `RecapLoader.parseRecap` 用 `JSON.parse` 代替正则，或新增 `RecapGenerator` 专门产 `Recap` 类型

3. **P3**: 与 OpenClaw 上游沟通 `[context-overflow-precheck]` 后应调 `afterTurn()`，从源头解决状态同步问题
