## 一、目标

建立独立模块 `src/efficiency/`，量化 compaction 效果与上下文预算利用效率，产出 per-session + 跨 session 的效率报告。**不改变现有 compaction 行为**（纯观测性，零回归风险）。

## 二、度量维度（三个核心指标）

### 1. Utilization %（利用率）

```
utilization = currentTokens / effectiveBudget
```

- `effectiveBudget` = `maxContextTokens × effectiveWindowRatio`（复用 model-profile 已有字段），或在已计算 MECW 时用 `mecwTokens`。
- 记录每次 `shouldCompact` 检查点的利用率，形成时间序列。

### 2. Waste metrics（浪费度量）

两个子指标：

- **压缩偏差（compaction delta）**：`recordCompaction` 时计算 `tokensAfter` vs `targetTokens` 的误差率 `|tokensAfter - targetTokens| / targetTokens`。衡量压缩是否「到位」。
- **触发偏差（trigger gap）**：`tokensBefore - threshold`，正 = 过晚触发（已超阈值才压），负 = 过早（阈值内就压）。衡量阈值是否合理。

### 3. Cache hit rate correlation（缓存命中率关联）

- 复用 `OptimizerMetricsCollector.getCacheHitRate()`。
- 关联：在一次 compaction 决策中，同时记录当时的 cache hit rate，输出 `{ utilization, cacheHitRate }` 对，供后续分析「利用率 vs 缓存命中」的相关性。

## 三、模块结构

```
src/efficiency/
  types.ts                # 类型：EfficiencyMetric, EfficiencyReport, 等
  ContextEfficiencyMetrics.ts   # 核心收集器
  index.ts                # barrel export
```

### 核心类 `ContextEfficiencyMetrics`

```ts
class ContextEfficiencyMetrics {
  recordCheckpoint(sessionId, modelId, currentTokens, budget?, taskType?): void
  recordCompaction(sessionId, tokensBefore, tokensAfter, targetTokens, threshold): void
  recordCacheContext(sessionId, cacheHitRate): void
  getSessionReport(sessionId): EfficiencyReport | undefined
  getAggregateReport(modelId?): EfficiencyReport  // 跨 session 聚合
  resetSession(sessionId): void
  clear(): void
}
```

### 类型（types.ts）

```ts
interface EfficiencyMetric {
  sessionId: string;
  modelId: string;
  utilization: number;        // 0-1
  effectiveBudget: number;
  currentTokens: number;
  timestamp: number;
}

interface WasteMetric {
  sessionId: string;
  compactionDeltaRate: number;  // |after-target|/target
  triggerGap: number;           // before - threshold
  timestamp: number;
}

interface EfficiencyReport {
  sessionId?: string;
  avgUtilization: number;
  peakUtilization: number;
  utilizationSamples: number;
  avgCompactionDeltaRate: number;
  avgTriggerGap: number;
  cacheHitRate: number;         // 最新或平均，视实现
  compactionCount: number;
  timeRange: { start: number; end: number };
}
```

## 四、与现有代码的集成点（不改变其语义）

1. **`ProactiveCompactionController`**：
   - `shouldCompact()` 已返回 `currentTokens`/`threshold`/`targetTokens`，是 utilization + triggerGap 的数据源。
   - `recordCompaction()` 已记录 `tokensBefore`/`tokensAfter`，是 compactionDelta 的数据源。
   - **集成方式**：在 controller 内（或调用方）调用 `ContextEfficiencyMetrics` 的 record 方法 `recordCheckpoint`/`recordCompaction`。为避免侵入，优先采用「注入 metrics 实例 + 在既有方法内追加 record 调用」的轻量方式。

2. **`OptimizerMetricsCollector`**：`getCacheHitRate()` 已有，直接复用。

3. **`OptimizerObserver`**：可选新增 `ctx.efficiency.checkpoint` 事件（导出到 claw-obs），但**非本迭代必须**（告警/导出是可选尾巴）。

> ⚠️ 关键约束：新增的 record 调用**不得改变** `shouldCompact` 的返回值语义、`recordCompaction` 的状态更新，只做「额外的观测记录」。

## 五、设计要点 / 边界

- **纯观测性**：本模块只读数据 + 计算 + 报告，不写入任何会影响 compaction 决策的状态。
- **无自适应**：不引入任何「根据度量调整阈值」的逻辑（那是 v6.7.0）。
- **向后兼容**：默认不启用（或启用但零副作用），不破坏现有 85+ 测试。
- **单例 + 可注入**：提供 `contextEfficiencyMetrics` 单例，同时支持构造注入（便于测试）。

## 六、测试要求

- `tests/`（或 `src/` 内联 `.test.ts`）新增：
  - `ContextEfficiencyMetrics` 各 record/get 方法的单测
  - utilization / waste / cache 计算正确性
  - per-session vs aggregate 报告
  - 与 controller 集成的集成测（不改变 shouldCompact/recordCompaction 语义）
- 目标 +6 测试文件；现有 85+ 全绿。
